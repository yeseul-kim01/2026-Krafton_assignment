# 17. 머지 정렬 (Merge Sort)

## 구현 내용

분할 정복(Divide and Conquer) 방식의 머지 정렬. 배열을 절반으로 나누고, 각각을 정렬한 후 병합한다.

- `merge(arr, left, mid, right)`: 정렬된 두 부분 배열을 하나로 병합
- `merge_sort_helper(arr, left, right)`: 재귀 함수. 반으로 쪼개고, 양쪽이 끝나면 병합
- `merge_sort(arr)`: 진입점

## 공부하면서 이해한 것

### 1. 분할 -> 정복 -> 병합

```python
if left >= right:          # base case: 원소 1개면 이미 정렬된 상태
    return
mid = (left + right) // 2  # 중간 지점 계산
merge_sort_helper(arr, left, mid)       # 왼쪽 절반 재귀 정렬
merge_sort_helper(arr, mid + 1, right)  # 오른쪽 절반 재귀 정렬
merge(arr, left, mid, right)            # 정렬된 두 절반을 병합
```

- base case가 `left >= right`인 이유: 원소가 1개인 구간은 그 자체로 정렬되어 있으므로 더 쪼갤 필요가 없다
- merge가 재귀 호출 두 개 "다음"에 오는 것이 핵심. 양쪽이 각각 정렬 완료된 후에야 병합할 수 있다. 그래서 실행 순서를 보면 가장 작은 조각부터 병합이 일어난다 (아래 시각화 참고)

### 2. merge의 세 단계

```python
left_arr = arr[left:mid + 1]        # 왼쪽 부분을 임시 배열로 복사
right_arr = arr[mid + 1:right + 1]  # 오른쪽 부분을 임시 배열로 복사

i = j = 0   # 각 임시 배열에서 읽을 위치
k = left    # 원본 배열에 쓸 위치
```

- 1단계: 두 임시 배열의 맨 앞끼리 비교해서 작은 쪽을 arr[k]에 넣고, 그쪽 포인터만 전진
- 2단계, 3단계: 한쪽이 먼저 소진되면 남은 쪽을 그대로 이어 붙임 (남은 쪽도 이미 정렬되어 있으므로 비교 불필요)
- 임시 배열로 복사해두는 이유: arr에 결과를 덮어쓰면서 진행하기 때문에, 복사본이 없으면 아직 읽지 않은 원본 값이 지워진다

### 3. 안정 정렬인 이유

비교 조건이 `left_arr[i] <= right_arr[j]`라서 값이 같으면 왼쪽(원래 앞에 있던 쪽)을 먼저 넣는다. 같은 값의 상대 순서가 유지되므로 안정 정렬(stable sort)이다. `<`로 바꾸면 같은 값일 때 오른쪽이 먼저 들어가서 안정성이 깨진다.

## 재귀 호출 시각화 - merge_sort([38, 27, 43, 3, 9, 82, 10])

실제 실행을 추적한 결과. #번호는 호출 순서, 들여쓰기는 재귀 깊이.

```
#1  ms(0, 6) 구간=[38, 27, 43, 3, 9, 82, 10]  mid=3 -> 분할
  #2  ms(0, 3) 구간=[38, 27, 43, 3]  mid=1 -> 분할
    #3  ms(0, 1) 구간=[38, 27]  mid=0 -> 분할
      #4  ms(0, 0) [38] -> base case 종료
      #5  ms(1, 1) [27] -> base case 종료
      merge 1번째: [38] + [27] -> [27, 38]
    #6  ms(2, 3) 구간=[43, 3]  mid=2 -> 분할
      #7  ms(2, 2) [43] -> base case 종료
      #8  ms(3, 3) [3]  -> base case 종료
      merge 2번째: [43] + [3] -> [3, 43]
    merge 3번째: [27, 38] + [3, 43] -> [3, 27, 38, 43]
  #9  ms(4, 6) 구간=[9, 82, 10]  mid=5 -> 분할
    #10 ms(4, 5) 구간=[9, 82]  mid=4 -> 분할
      #11 ms(4, 4) [9]  -> base case 종료
      #12 ms(5, 5) [82] -> base case 종료
      merge 4번째: [9] + [82] -> [9, 82]
    #13 ms(6, 6) [10] -> base case 종료
    merge 5번째: [9, 82] + [10] -> [9, 10, 82]
  merge 6번째: [3, 27, 38, 43] + [9, 10, 82] -> [3, 9, 10, 27, 38, 43, 82]
```

- merge_sort_helper 총 호출 횟수: 13회, merge 총 호출 횟수: 6회
- 호출은 왼쪽 절반을 끝까지 파고든 후(#1 -> #2 -> #3 -> #4) 돌아오면서 병합한다. 오른쪽 절반(#9~)은 왼쪽이 완전히 끝난 뒤에야 시작됨
- 병합 순서를 보면 [38]+[27]처럼 가장 작은 조각부터 시작해서 점점 큰 덩어리로 합쳐진다. "분할은 위에서 아래로, 병합은 아래에서 위로"

참고: 파일 상단 주석의 분할 그림은 [38, 27, 43] / [3, 9, 82, 10] (3-4 분할)로 그렸는데, 실제 코드는 mid = (0+6)//2 = 3이라 [38, 27, 43, 3] / [9, 82, 10] (4-3 분할)로 나뉜다. 왼쪽 구간이 mid를 "포함"하기 때문 (`arr[left:mid+1]`).

## 시간 복잡도 - 퀵 정렬과 비교

| 구분 | 머지 정렬 | 퀵 정렬 |
|---|---|---|
| 평균 | O(N log N) | O(N log N) |
| 최악 | O(N log N) | O(N^2) |
| 추가 메모리 | O(N) (임시 배열) | O(1) (제자리 교환) |
| 안정성 | 안정 | 불안정 |

머지 정렬은 입력이 어떻게 생겼든 항상 정확히 반으로 나누므로 최악의 경우가 없다 (테스트 케이스 3의 역순 배열도 동일하게 O(N log N)). 대신 병합할 때마다 임시 배열을 만들어서 메모리를 더 쓴다. 퀵 정렬과 정확히 반대의 트레이드오프.
