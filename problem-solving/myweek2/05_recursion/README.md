# 05. 재귀 함수 - 팩토리얼과 피보나치

## 구현 내용

재귀의 기본 구조(base case + recursive case)로 팩토리얼과 피보나치 구현.

## 이 문제를 왜 냈을까

팩토리얼과 피보나치는 같은 재귀인데 호출 구조가 완전히 다르다. 팩토리얼은 한 줄로 내려가는 선형 재귀, 피보나치는 갈래가 둘로 갈라지는 트리 재귀. 이 차이가 "재귀가 언제 효율적이고 언제 폭발하는지"를 보여주기 때문에 둘을 묶어서 낸 것 같다. 피보나치의 비효율을 몸으로 느끼고 나면 메모이제이션/DP가 왜 필요한지가 자연스럽게 따라온다.

## 풀이

```python
def factorial(n):
    if n == 0 or n == 1:      # base case
        return 1
    return n * factorial(n - 1)

def fibonacci(n):
    if n == 0:                # base case 1
        return 0
    elif n == 1:              # base case 2
        return 1
    return fibonacci(n - 1) + fibonacci(n - 2)
```

- 피보나치의 base case가 두 개인 이유: recursive case가 n-1과 n-2 두 곳으로 내려가므로, 바닥도 두 개(0과 1)를 깔아야 fib(2) = fib(1) + fib(0)이 안전하게 멈춘다. base case가 n == 0 하나뿐이면 fib(1)이 fib(0) + fib(-1)로 내려가 무한 재귀가 됨

## 재귀 호출 시각화 (실제 실행 추적)

### factorial(5) - 선형 재귀, 총 5회 호출

```
#1 factorial(5)
  #2 factorial(4)
    #3 factorial(3)
      #4 factorial(2)
        #5 factorial(1)   -> base case, 1 반환
         -> 2 * 1 = 2 반환
       -> 3 * 2 = 6 반환
     -> 4 * 6 = 24 반환
   -> 5 * 24 = 120 반환
```

내려갈 때는 계산 없이 호출만 쌓이고, base case에 닿은 뒤 올라오면서 곱셈이 일어난다. n이 1 줄어들 때 호출 1회라서 호출 횟수 = n, 즉 O(N).

### fibonacci(5) - 트리 재귀, 총 15회 호출

```
#1 fib(5)
  #2 fib(4)
    #3 fib(3)
      #4 fib(2)
        #5 fib(1)
        #6 fib(0)
      #7 fib(1)
    #8 fib(2)
      #9 fib(1)
      #10 fib(0)
  #11 fib(3)
    #12 fib(2)
      #13 fib(1)
      #14 fib(0)
    #15 fib(1)
```

호출 순서를 보면 왼쪽(n-1)을 끝까지 파고든 후 오른쪽(n-2)으로 넘어간다. 문제는 중복: fib(3)이 2번(#3, #11), fib(2)가 3번(#4, #8, #12), fib(1)은 5번 계산된다. 같은 값을 이미 구해놓고 기억하지 않아서 다시 구하는 것.

### 호출 횟수 증가 추이 (실측)

| n | fib(n) 호출 횟수 |
|---|---|
| 5 | 15 |
| 10 | 177 |
| 15 | 1,973 |
| 20 | 21,891 |

n이 5 늘 때마다 호출이 약 11배씩 는다. O(2^N)에 가까운 지수적 증가라서, 테스트의 fib(15)는 답이 610인데 그걸 구하려고 함수를 1,973번 부른 셈이다.

## 개선 방향

- 메모이제이션: 한 번 계산한 fib(k)를 dict에 저장하고 재사용하면 각 k당 1번씩만 계산 -> O(N). 파이썬은 @functools.lru_cache 데코레이터 한 줄로 됨
- 반복문(DP): 앞에서부터 두 변수만 갱신하며 올라가면 O(N) 시간, O(1) 공간
- 파이썬 재귀 깊이 제한: 기본 약 1000이라 factorial(2000)은 RecursionError가 남. 콜 스택이 실제 메모리(프레임)를 쌓기 때문이며, 깊이가 깊어질 수 있으면 반복문 전환을 고려해야 함

## 실무에서

재귀 자체는 트리/그래프 탐색(DFS), 디렉터리 순회, JSON 같은 중첩 구조 파싱처럼 "구조가 재귀적인 데이터"를 다룰 때 자연스럽다. 반면 피보나치처럼 하위 문제가 겹치는 계산은 재귀 그대로 두면 지수 폭발하므로 캐싱(메모이제이션)이 필수 - 함수 결과 캐싱은 실무에서도 lru_cache로 자주 쓰는 패턴.
