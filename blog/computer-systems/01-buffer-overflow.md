## 1. 컴퓨터는 코드와 데이터를 구분하지 못 한다!

컴퓨터 메모리에는 명령어(코드를 일컫음)와 데이터가 같이 들어있는데요. 그런데 CPU는 메모리 속 어떤 바이트가 "실행해도 되는 명령어"인지 아니면 단순히 "저장된 값"인지를 구분하지 못합니다.

CPU는 단순히 "지금 여기 가리키는 주소"의 바이트를 명령어라고 믿고 실행할 뿐임.

( 여기서 "지금 여기"를 가리키는 게 **PC**라고 하는데, PC는 "다음에 실행할 명령어의 메모리 주소"를 담는 CPU 안의 작은 레지스터입니다. 백엔드 지식으로 설명하자면 Kafka 컨슈머가 "다음에 읽을 offset"을 기억하듯, PC는 "다음에 실행할 명령어 위치"를 기억하죠. 그런데 함수를 호출(`call`)하면 "끝나고 돌아올 주소"를 스택에 저장해두고, 함수가 끝날 때(`ret`) 그 주소를 다시 PC에 넣습니다. 버퍼 오버플로우는 바로 이 스택에 저장된 복귀 주소를 덮어써서, `ret` 순간 CPU가 공격자가 원하는 주소를 PC에 넣도록 만드는 공격입니다! 복귀 주소를 덮어쓴다는 표현이 어색할 거 같은데, 이건 밑에서 언급하겠습니다. )

이러한 CPU의 특성을 생각해보면, 의도한 공격은 "내가 넣은 데이터를 CPU가 명령어로 실행하게 만드는 것"이라고 이해할 수 있을 듯 합니다. 즉 "프로그램이 갈 주소를 정해버리는" 겁니다.

## 2. 비유

버퍼 = 정해진 칸 수의 사물함

```
[ 신발장 64칸 ]  [ 관리인이 적어둔 "퇴근 후 갈 집 주소" ]
```

원래는 신발장 64칸에만 신발을 넣어야 되는데, 누가 100켤레를 욱여넣으면 그 옆에 있는 집 주소까지 메모로 덮어쓰게 됩니다. 그렇다면 기존에 원래 갈 주소 외에 공격자가 의도적으로 욱여넣은 주소로 이동할 수 있는 겁니다. 좀 더 자세한 플로우를 생각해보면,

- 원래는 신발장 64칸에 신발만 넣어야 함.
- 그런데 누가 신발을 100켤레 욱여넣으면?
- 신발장을 넘쳐서 옆에 붙어있는 "집 주소" 메모까지 덮어써 버림.
- 이제 관리인은 퇴근할 때 (덮어써진) 엉뚱한 주소로 감.
- 공격자가 그 주소 자리에 자기 집 주소(=공격 코드 위치)를 적어두면? → 관리인(프로그램)이 공격자가 원하는 곳으로 끌려감.

여기서 이제 신발장 64칸을 `char buf[64]` 같은 버퍼로 보면 되고, 집 주소를 함수가 끝나고 돌아가야 됐던 **return address**라고 이해하면 됩니다.

코드로 생각을 해보면,

```c
void handle_request(int sock) {
    char buf[64];              // 64바이트짜리 상자
    read(sock, buf, 4096);     // 근데 네트워크에서 최대 4096바이트를 읽음!
    ...
}
```

- 64칸밖에 없는데 4096칸을 받아버림.
- 넘친 데이터가 옆에 있는 return address(복귀 주소)를 덮어씀.
- 함수가 끝날 때 CPU는 덮어써진 주소로 점프 → 공격자가 원하는 코드 실행.

이렇게 스택의 return address를 덮어쓰는 기법을 **스택 스매싱**이라고 부릅니다. 그럼 여기서 return address는 언제 생기는건지도 짚어보겠습니다.

## 3. return address

저는 백엔드 개발이 좀 익숙해서, 백엔드 개발자 입장에서 잘 와닿는 표현으로 이해했습니다.

> return address는 특별한 상황에서 생기는 게 아닌 **함수를 호출할 때마다 자동으로 생긴다.**

예시로 설명해보겠습니다.

```python
def handle_request():
    data = parse_body()   # ← 여기서 잠깐 다른 함수로 떠남
    save_to_db(data)      # ← 여기서도 다른 함수로 떠남
    return response
```

이런 코드를 짰다고 가정을 해볼 때, `parse_body()`를 호출하면 CPU는 그 함수 코드로 점프하겠죠. 그런데 해당 함수가 끝나면 원래 하던 `handle_request`로 돌아와야 합니다. 그래서 CPU는 함수를 부르기 직전에 돌아올 주소 또한 스택에 적어둡니다.

### 백엔드 비유: 함수 호출 = 콜스택(Call Stack)

에러 터졌을 때 보는 **스택 트레이스(stack trace)** 기억나시죠?

```
  at save_to_db (db.py:42)
  at handle_request (server.py:15)   ← 여기로 돌아가야 함
  at main (app.py:3)
```

이 스택 트레이스가 바로 return address들이 쌓여있는 스택을 사람이 읽기 좋게 보여준 것입니다. 즉 return address는 이미 당신이 매일 보던 개념이에요. 함수 하나 부를 때마다 하나씩 쌓이는 "돌아갈 주소"입니다.

### 스택이란? (OS·하드웨어 관점)

여기서 스택에 대해 앞으로의 내용을 이해할 정도로만 정리하고 가겠습니다.

스택은 메모리의 한 영역입니다. 정확히는 함수 호출 정보를 쌓아두는 전용 공간인데, 우선 프로그램이 실행되면 OS는 그 프로세스의 메모리를 몇 개의 구역으로 나눠줍니다.

1. 코드가 있는 곳
2. 전역 데이터가 사용되는 곳
3. 함수가 호출될 때마다 쓰는 임시 메모리 = **스택** (LIFO 동작)

함수를 부르게 되면 그 함수의 전용 칸인 **스택 프레임**이 하나 쌓이고, 함수가 끝나면 그 칸이 지워집니다. 그리고 이 때 해당 스택 프레임 하나 안에는 세 가지가 같이 들어가는데,

1. 그 함수의 지역 변수 (← 바로 `char buf[64]`가 여기 삽니다)
2. 이전 프레임 정보 (저장된 베이스 포인터 `rbp` 등)
3. return address (복귀 주소)

![스택 프레임과 버퍼 오버플로우](assets/stack-frame.png)

핵심은 `buf[64]`와 `return address`가 같은 프레임 안 이웃에 있고요, 스택은 높은 → 낮은 주소로 자라는데 배열은 반대로 채워집니다. 그래서 `buf`가 넘치게 되면 위쪽의 return address까지 덮어쓰게 되는 겁니다.

이 지점에서 보게 되면, 공격을 받을 수 있는 지점이

1. 함수 안에 선언한 지역 변수와 return address가 같은 스택에 나란히 있고
2. 버퍼를 넘치게 하면 바로 옆의 return address까지 덮어쓰게 되며
3. 함수가 끝나면서 CPU는 덮어써진 그 값을 복귀 주소라 믿기 때문에 PC에 넣어, 원래 돌아갈 주소가 아닌 누군가 의도적으로 심어둔 주소로 점프하게 된다.

이 흐름으로 공격을 받을 수 있게 되는 겁니다.

## 4. 네트워크 요청이 어떻게 이 버퍼까지 도달하나 (전체 여정)

백엔드에서 `request.body` 하나 받는 게, 사실은 이 긴 여정의 끝입니다.

```
[클라이언트]
   │  1. HTTP 요청 전송 (POST /login, body에 데이터)
   ▼
[TCP/IP 로 쪼개짐]  요청이 여러 개의 패킷으로 나뉘어 인터넷을 건너감
   ▼
[서버의 NIC(랜카드)]  2. 패킷 도착
   ▼
[OS 커널]  3. 패킷을 조립해서 "소켓(socket)"의 수신 버퍼에 쌓아둠
   ▼
[당신의 서버 코드]  4. read(sock, buf, ...) / recv() 로 그 데이터를 읽어옴  ← 여기!
   ▼
[핸들러 함수]  5. buf 에 담긴 요청을 파싱해서 처리
```

문제가 터지는 곳은 정확히 4번인데, 저희가 쓰는 프레임워크(Spring, Express, Django...)는 내부적으로 이렇게 동작합니다.

```c
// 프레임워크/웹서버 내부 (보통 C로 짜여있음)
char buf[1024];
int n = recv(client_sock, buf, 8192, 0);   // 소켓에서 데이터를 buf로 읽음
```

- **소켓(socket)** = 네트워크로 들어온 데이터가 도착하는 "구멍/파이프"입니다. 백엔드에서 포트 열고 `listen` 하는 부분을 말하는 거고,
- `recv()` / `read()` = 그 구멍에서 데이터를 꺼내 버퍼에 담는 순간.
- 이때 "버퍼 크기(1024)보다 큰 데이터(8192)를 그대로 담으면" → 4번에서 오버플로우가 발생합니다.

### 그렇다면 왜 "네트워크"가 특별히 위험한가?

로컬 프로그램은 입력이 내 손안(파일, 키보드)이라 통제가 가능합니다. 하지만 네트워크 입력은 내가 보낸 게 아니기 때문에 크기도, 내용도 마음대로 조작이 가능하고요. 즉 "신뢰할 수 없는 입력(untrusted input)이 곧장 버퍼로 들어온다"는 게 핵심 위험 지점입니다.

그래서 이 취약점이 원격(remote)에서 터지면, 공격자가 서버에 로그인도 없이 코드를 실행할 수 있게 되는 겁니다.

> "클라이언트가 보낸 request body → 소켓 → recv() → 버퍼" 이 길목에서, 버퍼 크기 검사를 안 하면 오버플로우가 나고, 그게 원격 코드 실행이 된다. 그래서 항상 **입력 길이 검증(Content-Length 제한, 버퍼 경계 검사)** 이 백엔드 보안의 기본이 됩니다.

## 5. 그런데 이게 어떻게 "인터넷 전체"를 감염시킬까? (웜의 원리)

버퍼 오버플로우 하나로 남의 서버에서 내 코드를 실행시켰다고 칩시다.

1. 내 코드가 남의 서버에서 실행됨 → 원격 코드 실행(RCE) 성공
2. 그 코드가 다른 취약한 서버들을 스캔함 (아무 IP나 찔러봄)
3. 취약한 서버 발견하면 똑같은 공격을 그 서버에 또 쏨
4. 감염된 서버가 다시 2번부터 반복...

이렇게 사람 손 없이 스스로 복제하며 퍼지는 프로그램을 **웜(Worm)** 이라고 합니다.

```
1대 → 2대 → 4대 → 8대 → 16대 → ...  (기하급수적 폭증)
```

한 대가 여러 대를 감염시키니까 감염 속도가 지수함수가 됩니다.

## 6. Python / Java

위에서 설명드린 고전적인 버퍼 오버플로우는 사실상 C 언어 쪽의 문제입니다. C는 배열 크기 검사가 없지만, Python은 실행 중에 검사하고 튕겨내기 때문이고, Java도 마찬가지입니다.

```python
buf = [0] * 64      # 64칸 리스트
buf[100] = 65       # IndexError: list assignment index out of range
```

```java
byte[] buf = new byte[64];
buf[100] = 65;   // ArrayIndexOutOfBoundsException: Index 100 out of bounds
```

정리하자면,

- C는 검사를 하지 않고 빠르게! → 버퍼 오버플로우에 노출될 수 있다.
- Python / Java는 매번 검사해서 안전하지만 → 약간의 속도 저하가 있다.

물론 완전히 Python·Java가 안전한 건 아닙니다. 직접적인 스택 스매싱이 존재하지 않는 거지, 해당 언어의 인터프리터나 가상 머신은 C와 C++로 만들어져 있습니다. 그렇기에 자체 버그보다는 그 밑을 받쳐주는 C 엔진 쪽의 버그로 오버플로우가 터질 수는 있습니다.

다만 요즘에는 ① 스택 카나리 ② DEP / NX bit ③ ASLR 등의 방어가 있고, 요즘 공격은 오버플로우 대신 역직렬화 취약점, SQL 인젝션, 라이브러리 취약점 쪽으로 많이 옮겨갔다고 합니다.
