# 프로그램은 다른 프로그램에 의해 다른 형태로 번역된다

## 0. 한 줄 요약

> 우리가 쓴 `hello.c`(사람이 읽는 텍스트)는 CPU가 바로 못 읽는다.
> **전처리 → 컴파일 → 어셈블 → 링크** 4단계를 거쳐 **기계어 실행파일**로 "번역"된다.
> 각 단계는 서로 다른 프로그램이 담당한다.

```
hello.c  ──전처리(cpp)──▶  hello.i  ──컴파일(cc1)──▶  hello.s  ──어셈블(as)──▶  hello.o  ──링크(ld)──▶  hello
(소스)                    (전처리)                  (어셈블리)                (오브젝트)              (실행파일)
텍스트                    텍스트                    텍스트                    이진(기계어)            이진(실행가능)
```

> 이 실습은 macOS(Apple clang, arm64 CPU)에서 진행. 책(CSAPP)은 리눅스(gcc, x86-64)라
> 명령어 이름이 조금 다르지만 **4단계 개념은 완전히 동일**하다.

이 실습에 쓴 소스 → [code/hello/hello.c](code/hello/hello.c)

```c
#include <stdio.h>

int main()
{
    printf("hello, world\n");
    return 0;
}
```

각 단계 명령 (한 방에 하려면):
```bash
gcc -E hello.c -o hello.i   # 1) 전처리
gcc -S hello.i -o hello.s   # 2) 컴파일
gcc -c hello.s -o hello.o   # 3) 어셈블
gcc    hello.o -o hello     # 4) 링크
./hello                     # 실행 → hello, world
```

---

## 1단계. 전처리 (Preprocessing) → `hello.i`

**담당 프로그램:** 전처리기(cpp) │ **명령:** `gcc -E`

### 하는 일
`#`으로 시작하는 지시문을 처리한다.
- `#include <stdio.h>` → **stdio.h 파일 내용을 그 자리에 통째로 복사해 붙임**
- `#define` 매크로 치환, `#if` 조건부 컴파일 처리
- 결과물도 여전히 **사람이 읽는 C 텍스트** (아직 번역 아님, "붙여넣기" 단계)

### 실제 결과: 7줄이 583줄로 폭발
```
총 줄 수: 583 줄  (원본 hello.c는 7줄)
```
`stdio.h`와 그 안에서 또 include하는 파일들이 전부 딸려 들어와서 이렇게 커진다.
맨 아래에 **우리가 쓴 코드는 그대로** 남아있다:

```c
extern int __vsnprintf_chk (...);   // ← stdio.h 에서 딸려온 함수 선언들
# 2 "hello.c" 2

int main()                          // ← 여기부터가 내가 쓴 코드
{
    printf("hello, world\n");
    return 0;
}
```

**포인트:** `printf`의 "선언(prototype)"이 stdio.h에서 여기로 복사돼 들어왔다.
그래서 컴파일러가 "printf라는 함수가 있구나" 를 알게 됨. (정의가 아니라 선언만!)

---

## 2단계. 컴파일 (Compilation) → `hello.s`

**담당 프로그램:** 컴파일러(cc1) │ **명령:** `gcc -S`

### 하는 일
전처리된 C 코드를 **어셈블리어(assembly)** 로 번역한다.
- 여기서 처음으로 **CPU가 이해하는 언어에 가까워짐** (아직 텍스트지만)
- CPU 종류(arm64 / x86-64)마다 어셈블리가 **완전히 다름**

### 실제 결과 (arm64) — 핵심 부분만
```asm
_main:
	sub	sp, sp, #32            ; 스택에 32바이트 공간 확보 (함수 시작)
	stp	x29, x30, [sp, #16]    ; 되돌아갈 주소(x30=lr) 등을 스택에 저장 
	...
	adrp	x0, l_.str@PAGE        ; "hello, world\n" 문자열 주소를 x0에 준비
	add	x0, x0, l_.str@PAGEOFF ; (printf의 첫 인자로 전달)
	bl	_printf                ; printf 함수 호출 (branch with link)
	...
	ret                        ; 저장해둔 주소로 복귀 (함수 종료)

l_.str:
	.asciz	"hello, world\n"       ; 우리가 쓴 문자열은 여기 데이터로 들어감
```

**백엔드 연결점:** 앞에서 본 **return address**가 여기 실제로 보인다.
`stp ... x30` 이 "돌아갈 주소(link register)를 스택에 저장" 하는 명령이고,
맨 끝 `ret`이 "그 주소로 돌아가라"는 명령. **함수 호출의 실체가 어셈블리에 그대로 드러남.**

## 3단계. 어셈블 (Assembly) → `hello.o`

**담당 프로그램:** 어셈블러(as) │ **명령:** `gcc -c`

### 하는 일
어셈블리 텍스트를 **진짜 기계어(0과 1, 이진 바이트)** 로 번역한다.
- 결과물 `hello.o` = **오브젝트 파일**. 여기서부터 텍스트가 아니라 **바이너리.**
- 사람이 열면 깨져 보임 → 전용 도구(`objdump`, `xxd`)로 봐야 함.
- **아직 실행은 못 한다.** `printf`가 어디 있는지 아직 모르기 때문 (다음 단계에서 연결).

### 실제 결과: 어셈블리 한 줄 ↔ 기계어 바이트 대응
`objdump -d hello.o`:
```
   0: d10083ff   sub  sp, sp, #0x20      ← "d10083ff" 4바이트 = sub 명령 하나
   4: a9017bfd   stp  x29, x30, [sp,#0x10]
   ...
  20: 94000000   bl   0x20               ← printf 호출 자리인데 주소가 0! (미완성)
  30: d65f03c0   ret
```
- 왼쪽 `d10083ff` 같은 게 **실제 CPU가 먹는 기계어 바이트**.
- 오른쪽이 그걸 사람이 읽게 되돌린 어셈블리.
- 주목: `bl 0x20` 의 printf 주소가 **비어있음(0000)**. → 아직 printf 위치를 모름.

### 파일 성격 확인
```
$ file hello.o
hello.o: Mach-O 64-bit object arm64   ← "object" (부품, 실행파일 아님)
```

## 4단계. 링크 (Linking) → `hello` (실행파일)

**담당 프로그램:** 링커(ld) │ **명령:** `gcc`(옵션 없이)

### 하는 일
내 `hello.o` + **라이브러리(printf가 들어있는 libc)** 를 하나로 **합친다(연결).**
- 3단계에서 비어있던 `printf` 주소를 **실제 위치로 채워 넣음.**
- 이제 모든 조각이 연결돼서 **드디어 실행 가능한 완성품**이 됨.

### 실제 결과
```
$ file hello
hello: Mach-O 64-bit executable arm64   ← "executable" (실행 가능!)
```
```
$ ./hello
hello, world
```

### 왜 링크가 따로 필요한가? (백엔드 비유)
- `printf`는 내가 안 짰다. OS가 제공하는 **표준 라이브러리(libc)** 에 이미 있음.
- 링커가 "너가 부른 printf, 그건 저기 libc의 이 주소에 있어" 하고 **연결해주는 역할.**
- 백엔드로 치면 **`import` / 의존성 라이브러리(npm, pip, maven)를 실제로 끌어와 묶는 것**과 같은 개념.

## 4.5. 링크가 "정확히" 하는 일 (증거로 확인)

링커의 일은 크게 **세 가지**다. 방금 만든 파일로 하나씩 증거를 뽑아봤다.

### 일 ① 심볼 해석 (Symbol Resolution): "누가 뭘 쓰고, 누가 뭘 가졌나" 맞추기

`.o` 파일 안의 이름(심볼)들은 두 종류다.
- **정의됨(Defined):** "내가 이걸 가지고 있다" → 예: `main`
- **미정의(Undefined, U):** "내가 이걸 쓰는데, 어디 있는지는 모른다" → 예: `printf`

`nm hello.o` 결과:
```
0000000000000000 T _main       ← 내가 정의함 (주소 있음)
                 U _printf      ← U = Undefined, "printf 쓰는데 위치 모름. 링커가 찾아줘"
```

링커의 첫 번째 임무: **모든 U(미정의) 심볼을, 그걸 정의한 곳(라이브러리 등)과 짝지어준다.**
못 찾으면 그 유명한 **`undefined reference to 'printf'`** 링크 에러가 난다.

### 일 ② 재배치 (Relocation): 비워둔 주소 자리를 실제 주소로 채우기

어셈블 단계에선 printf가 어디 있을지 모르니, 호출 명령의 **주소 자리를 0으로 비워두고** "여기 나중에 채워야 함" 이라고 메모를 남긴다. 그 메모가 **재배치 레코드**다.

`objdump -r hello.o` (메모 목록):
```
OFFSET   TYPE                   VALUE
...0020  ARM64_RELOC_BRANCH26   _printf   ← "0x20 위치의 호출 명령에 printf 주소를 채워라"
```

이게 실제로 채워지는 걸 **링크 전/후 바이트 비교**로 확인할 수 있다:

```
[링크 전] hello.o
  20: 94000000   bl  0x20        ← 뒤 26비트가 전부 0 = "주소 미정" (자기 자신 가리킴)

[링크 후] hello (실행파일)
  100000480: 94000005   bl  0x100000494   ← 0000000 → 0000005 로 채워짐! 진짜 목적지 주소
```

명령어 바이트가 `94000000` → `94000005` 로 **실제로 바뀐 것**이 보인다.
이게 재배치의 핵심: **여러 조각을 합치면서 최종 메모리 주소를 확정하고, 비워뒀던 참조들을 그 주소로 메꾼다.**

### 잠깐, 어셈블러는 printf 주소를 왜 "모르나"?

결론: **어셈블러는 파일을 딱 하나씩, 서로 격리된 채로 번역하기 때문.** (이걸 *분리 컴파일 / separate compilation* 이라 부른다)

`gcc -c hello.s` 를 실행할 때, 어셈블러의 시야에는 **오직 hello.s 한 파일밖에 없다.** 그래서:

1. **printf는 이 파일에 없다.**
   printf의 코드는 완전히 다른 파일(libc)에 있다. 어셈블러는 그 파일을 **열어보지도 않는다.**
   당연히 "printf가 최종 메모리 몇 번지에 놓일지" 알 방법이 없다.

2. **설령 같은 파일에 있어도 최종 주소는 아직 못 정한다.**
   실제 주소는 **모든 .o 조각과 라이브러리를 다 모아 한 줄로 배치(layout)해봐야** 정해진다.
   내 `hello.o`가 앞에 놓일지, 다른 파일 뒤에 놓일지, 시작 번지가 몇인지 —
   이건 **전체를 다 본 사람만** 계산할 수 있다. 그게 바로 **링커**다.

> 비유: 이사할 집들의 **정확한 도로명 주소**는, 신도시 전체 배치도가 나와야 매길 수 있다.
> 건물(각 .o) 하나만 따로 짓는 시공사(어셈블러)는 "우리 동은 몇 번지"인지 모른다.
> 대신 "여기에 주소 들어갈 자리 비워둠" 이라고 표시(재배치 레코드)만 해둔다.
> 나중에 도시 전체를 총괄하는 사람(링커)이 배치도를 확정하고 번지를 다 채운다.

**그럼 왜 굳이 이렇게 따로따로 하냐?** → 이게 오히려 큰 장점이라서다:
- 파일 1000개짜리 프로젝트에서 **한 파일만 고치면, 그 파일의 .o만 다시 만들고** 나머지 999개는 재사용 → 빌드 초고속. (`make`의 원리)
- printf 같은 표준 함수를 **모든 프로젝트가 매번 재컴파일할 필요 없이**, 미리 컴파일된 라이브러리로 공유.

즉 "모르는 것"이 아니라, **"각자 자기 것만 번역하고, 주소 확정이라는 전체 작업은 링커에게 위임"** 하도록 일부러 설계한 것.

### 일 ③ 조각 합치기 (여러 .o + 라이브러리 → 하나)
- 프로젝트가 커지면 `.o`가 여러 개다. 링커가 이들의 같은 종류 구역(코드는 코드끼리, 데이터는 데이터끼리)을 **하나로 모아 배치**한다.
- 그리고 표준 라이브러리도 연결한다.

`otool -L hello` (이 실행파일이 의존하는 라이브러리):
```
hello:
	/usr/lib/libSystem.B.dylib   ← printf가 들어있는 시스템 라이브러리에 의존
```

### 정적 링크 vs 동적 링크 (중요한 갈림길)
위 `otool -L` 결과가 힌트다. 요즘 printf는 실행파일 안에 **복사돼 들어오지 않는다.**

| | 정적 링크 (static) | 동적 링크 (dynamic) — 오늘날 기본 |
|---|---|---|
| 방식 | 라이브러리 코드를 **실행파일 안에 복사** | 라이브러리는 **밖에 두고, 실행할 때 연결** |
| printf | 내 파일 안에 printf 기계어가 통째로 있음 | 실행 순간 OS의 `dyld`(동적 링커)가 libSystem에서 찾아 연결 |
| 파일 크기 | 큼 | 작음 |
| 장점 | 혼자서 실행됨(의존성 X) | 메모리 절약, 라이브러리 업데이트 시 재컴파일 불필요 |

- 그래서 위 [증거 4]의 `bl` 목적지는 printf 본체가 아니라 **`__stubs`(대리 창구)** 주소다.
- 실행하는 순간 동적 링커가 그 창구를 실제 printf 주소로 연결한다. (이걸 **로드타임/런타임 링킹**이라 부름)

> **한 문장 정리:**
> 링커 = ① 흩어진 "쓴다(U)"와 "가졌다"를 짝짓고(심볼 해석), ② 비워뒀던 주소를 실제 주소로 채우고(재배치), ③ 조각과 라이브러리를 하나로 묶어 **실행 가능한 완성품**을 만드는 프로그램.

## 5. 파일별 정리 표

| 단계 | 명령 | 결과 파일 | 형태 | 사람이 읽나? | 실행되나? |
|---|---|---|---|---|---|
| 원본 | — | `hello.c` (7줄) | 텍스트(C) | O | X |
| 1 전처리 | `gcc -E` | `hello.i` (583줄) | 텍스트(C) | O | X |
| 2 컴파일 | `gcc -S` | `hello.s` | 텍스트(어셈블리) | △ (전문) | X |
| 3 어셈블 | `gcc -c` | `hello.o` | **이진(기계어)** | X (도구 필요) | X (미완성) |
| 4 링크 | `gcc` | `hello` | **이진(실행파일)** | X | O |

## 6. 파일을 직접 열어보는 명령어 모음

```bash
# 텍스트 파일 (그냥 열면 됨)
cat hello.i          # 전처리 결과
cat hello.s          # 어셈블리

# 바이너리 파일 (전용 도구 필요)
file hello.o         # 파일 종류 확인 (object/executable)
xxd  hello.o | head  # 16진수 바이트 덤프로 보기
objdump -d hello.o   # 역어셈블: 기계어 바이트 ↔ 명령어 대응 보기
objdump -d hello     # 최종 실행파일 역어셈블 (printf 주소가 채워진 걸 확인 가능)
```

> **왜 4단계로 쪼개져 있나?**
> ① 각 단계를 **다른 전문 프로그램**이 맡아 역할 분리 → 유지보수·최적화 쉬움.
> ② 특히 **링크**를 분리한 덕분에, 소스 하나 고쳐도 **바뀐 .o만 다시 만들고 나머진 재사용** 가능
> (이게 대규모 프로젝트의 빌드 속도를 살리는 핵심 — `make`가 하는 일).
