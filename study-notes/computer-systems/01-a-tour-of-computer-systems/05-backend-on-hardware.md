# 백엔드 서버가 하드웨어에서 실행되는 원리 (실무 연결)

> CSAPP 1장의 **프로세스 · 스레드 · 메모리 · 디스크** 개념을,
> 내가 실제로 만든 **도깨비 프로젝트**(NestJS 서버 + FastAPI AI 서버 + Redis)에 대입해 정리.
> 요청대로 **Spring Boot**도 함께 비교한다.

```
[도깨비 실제 구조]
  dokkaebi-server (NestJS / Node.js)  ── REST + Socket.io
  dokkaebi-ai     (FastAPI / Python)  ── LLM 서빙 (uvicorn, llm_semaphore로 동시성 제어)
  Redis (dump.rdb)                    ── 캐시/세션
```

---

## 0. 큰 그림: 서버도 결국 "하나의 프로세스"다

`java -jar app.jar` 든 `uvicorn app.main:app` 이든 `npm run start:prod` 든,
서버를 켠다는 건 결국 앞 단원에서 배운 그거다:

> **디스크에 있던 실행 코드를 메모리로 올려서, CPU가 인스트럭션을 읽어 실행하는 프로세스를 하나 만드는 것.**

웹서버가 특별한 게 아니라, **"종료되지 않고 계속 돌면서 네트워크 요청을 기다리는 프로세스"** 일 뿐이다.
(1장 버퍼 오버플로우 문서에서 본 `recv()` 로 소켓을 계속 읽는 그 무한 루프가 서버의 본질)

## 1. Spring Boot 가 켜질 때 — 하드웨어 관점

### 부팅 순서
```
1. java -jar app.jar 실행
   → [디스크]의 JVM(java) 실행파일이 [메모리]로 로드돼 프로세스 시작
   → 이 프로세스가 바로 JVM(자바 가상 머신)

2. JVM이 app.jar 안의 .class(바이트코드)들을 [디스크] → [메모리]로 읽어들임
   → "클래스 로딩". 앞 단원의 '디스크→메모리 로드'와 완전히 동일

3. JIT 컴파일: 바이트코드를 실행 중에 CPU 기계어로 번역
   → 자주 쓰는 코드일수록 기계어로 바꿔 빠르게 (인터프리터 + 컴파일러 혼합)

4. 내장 톰캣(Tomcat)이 포트 8080 소켓을 열고 listen
   → 이제 요청을 기다리는 상태

5. 요청이 오면 → 스레드 풀에서 스레드 하나 배정 → 처리 → 응답
```

### 핵심: JVM은 "가상 프로세서"
- 자바 바이트코드는 실제 CPU(arm64/x86) 인스트럭션이 아니다.
- JVM이 **바이트코드를 진짜 CPU 인스트럭션으로 통역**해준다. → 그래서 "어느 CPU/OS든 돌아감"(WORA).
- CSAPP 용어로: **JVM = 소프트웨어로 만든 가상 프로세서**, 그 위에서 내 코드가 프로세스처럼 돈다.

### Spring Boot 의 동시성 모델: **Thread-per-request (요청당 스레드)**
```
요청 A ──▶ [스레드 1] 이 처음부터 끝까지 담당 (DB 기다리는 동안 이 스레드는 '블로킹'되어 놀며 대기)
요청 B ──▶ [스레드 2]
요청 C ──▶ [스레드 3]
...톰캣 기본 스레드 풀 200개
```
- 요청 하나에 **스레드 하나**를 통째로 붙임.
- DB 조회로 0.1초 기다리면, **그 스레드는 그동안 아무것도 못 하고 대기(blocking).**
- 동시 요청이 스레드 풀(기본 200개)을 넘으면 → 큐에서 대기 → 느려지거나 타임아웃.

## 2. FastAPI(도깨비-ai) 가 켜질 때 — 하드웨어 관점

### 부팅 순서
```
1. uvicorn app.main:app 실행
   → [디스크]의 python 인터프리터가 [메모리]로 로드돼 프로세스 시작

2. 파이썬이 main.py 부터 import 되는 모듈들을 [디스크] → [메모리]로 읽어 해석
   → create_app() 실행 = FastAPI 앱 객체 생성, 라우터 등록 (내 코드!)

3. uvicorn이 포트 소켓을 열고 listen → 요청 대기

4. 요청이 오면 → 이벤트 루프가 코루틴으로 처리
```

### FastAPI 의 동시성 모델: **비동기 이벤트 루프 (async event loop)**
Spring Boot와 근본적으로 다르다.
```
[스레드 딱 1개]가 이벤트 루프를 돌림:
  요청 A 처리 시작 → LLM 응답 기다려야 함(await) → "기다리는 동안 A 잠깐 내려놓음"
  → 요청 B 처리 시작 → 얘도 await → 내려놓음
  → 요청 C 처리...
  → A의 LLM 응답 도착 → 다시 A 이어서 처리
```
- **스레드 하나로 수많은 요청을 번갈아 처리** (요리사 1명이 여러 냄비 동시에 돌보듯).
- 핵심은 **"기다리는 시간(I/O)에 딴 요청을 처리"** 한다는 것. 그래서 I/O 대기가 많은 작업(LLM 호출, DB, 네트워크)에 강함.
- 단, **CPU를 오래 쓰는 무거운 계산**을 이벤트 루프에서 하면 → 그동안 다른 요청 전부 멈춤(루프가 막힘).

### 도깨비-ai의 `llm_semaphore` 가 바로 이 맥락
```python
"%s 기동 (... sem=%d ...)", s.llm_semaphore   # main.py 기동 로그에 찍히는 그거
```
- 이벤트 루프는 요청을 무한정 받아들일 수 있지만, **LLM 동시 호출이 너무 많으면** 외부 API 한도·메모리가 터진다.
- **세마포어(semaphore) = "동시에 N개까지만 통과" 하는 게이트.** N+1번째부터는 앞이 끝날 때까지 대기.
- 즉 이벤트 루프의 "무한 동시성"을 **의도적으로 N개로 제한**하는 동시성 제어 장치.
- 이게 OS의 동기화 개념(세마포어)을 백엔드에서 실제로 쓰는 예. CSAPP 뒤쪽 동시성 단원과 직결.

## 3. 도깨비-server(NestJS) — 실제 내 서버는 이 모델

내 `dokkaebi-server`는 Spring Boot가 아니라 **NestJS(Node.js)** 다. 그런데 재밌게도
**Node.js도 FastAPI와 똑같은 "단일 스레드 이벤트 루프"** 계열이다.

```
Node.js: 메인 스레드 1개가 이벤트 루프를 돌림 (FastAPI의 async와 사실상 같은 철학)
  → I/O(DB, Redis, 소켓)는 논블로킹으로 던져두고, 완료되면 콜백/await로 이어받음
  → Socket.io 실시간 통신에 이 모델이 특히 잘 맞음
```

> 그래서 내 프로젝트는 **server(NestJS)도, ai(FastAPI)도 둘 다 이벤트 루프 기반**이다.
> Spring Boot(스레드 풀)만 다른 진영. 이 대비를 이해하는 게 이 문서의 핵심.

## 4. 세 프레임워크 동시성 모델 비교

| | **Spring Boot** | **FastAPI** (도깨비-ai) | **NestJS** (도깨비-server) |
|---|---|---|---|
| 언어/런타임 | Java / JVM | Python / uvicorn | Node.js / V8 |
| 프로세스 위 실행 형태 | JVM(가상머신) 위 | 파이썬 인터프리터 위 | V8 엔진 위 |
| 동시성 모델 | **스레드 풀** (요청당 스레드) | **단일 스레드 이벤트 루프** (async) | **단일 스레드 이벤트 루프** |
| I/O 대기 중 | 그 스레드 블로킹(놀며 대기) | 딴 요청 처리 (논블로킹) | 딴 요청 처리 (논블로킹) |
| 강점 | CPU 작업·복잡한 로직, 성숙한 생태계 | I/O 많은 작업(LLM/API/DB) | 실시간(Socket.io), I/O |
| 약점 | 스레드 많으면 메모리·문맥교환 비용 | 무거운 CPU 계산이 루프를 막음 | 동일 (CPU 계산 취약) |
| 동시성 늘리는 법 | 스레드 풀 크기 ↑ | **프로세스(워커) 여러 개**(gunicorn -w) | 프로세스 여러 개(PM2 cluster) |

> 한 줄 요약:
> **Spring Boot = "요청마다 일꾼(스레드) 한 명씩 붙임".
> FastAPI/NestJS = "일꾼 한 명이 여러 요청을 번갈아 돌봄(기다리는 시간에 딴 일)".**

## 5. 하드웨어 3대 개념 ↔ 백엔드 실무 매핑

### ① 스레드(Thread)
> **스레드 = 한 프로세스 안에서 인스트럭션을 실행하는 "일꾼" 한 명.** 한 프로세스는 여러 스레드를 가질 수 있다.

- 프로세스 = 회사, 스레드 = 그 회사 직원들. 직원들은 **회사 자원(메모리)을 공유**한다.
- Spring Boot: 요청마다 직원 한 명 배정 → 직원(스레드) 200명 풀.
- FastAPI/NestJS: 유능한 직원 1명이 여러 일을 번갈아 처리.
- **실무 함정:** 스레드들은 메모리를 공유하므로, 여러 스레드가 같은 데이터를 동시에 건드리면 **경쟁 상태(race condition)**. 그래서 락(lock)·세마포어가 필요. (도깨비-ai의 `llm_semaphore`가 그 예)

### ② 메모리(Memory)
> 실행 중 데이터가 올라가는 **책상**. 전원 끄면 날아감(휘발성).

- **힙(Heap):** 객체·데이터가 사는 곳. Java는 GC(가비지 컬렉터)가 안 쓰는 객체 자동 청소.
- **스택(Stack):** 함수 호출/지역변수 (1장 버퍼 오버플로우의 그 스택!). **스레드마다 각자 스택**을 가짐.
- **실무 연결:**
  - `OutOfMemoryError`(Java) / 컨테이너 OOM Kill = 힙이 꽉 참. → JVM `-Xmx`로 힙 크기 조절.
  - Redis(도깨비 `dump.rdb`)가 빠른 이유 = 데이터를 **디스크가 아닌 메모리**에 두기 때문.
  - 스레드를 많이 만들수록 스택 메모리도 그만큼 늘어남 → Spring Boot 스레드 풀 무한정 못 키우는 이유.

### ③ 디스크(Disk)
> **영구 저장 창고.** 느리지만 전원 꺼도 유지.

- 실행파일/코드가 사는 곳: `app.jar`, `.class`, `main.py`, `node_modules` → 부팅 때 메모리로 로드.
- DB의 실제 데이터 파일, 로그 파일, 업로드된 이미지.
- **실무 연결:**
  - 서버가 느리다? → "디스크 I/O 병목"인지 "CPU 병목"인지 구분하는 게 튜닝의 시작.
  - Redis 캐시를 쓰는 이유 = **느린 디스크(DB) 대신 빠른 메모리**에서 읽으려고. (1장 "디스크→메모리로 옮겨 빠르게"의 실무판)
  - `dump.rdb` = Redis가 메모리 내용을 주기적으로 디스크에 스냅샷 저장한 것(재시작 대비).

## 6. 요청 하나가 처리되는 전체 흐름 (도깨비 예시)

```
[사용자] 도깨비 앱에서 "지역 추천" 요청
   │  HTTP 요청 (1장: 패킷 → NIC → 커널 → 소켓)
   ▼
[dokkaebi-server / NestJS]  이벤트 루프가 요청 받음
   │  ├─ Redis 캐시 확인 (메모리에서 초고속 조회)
   │  └─ 캐시 없으면 → dokkaebi-ai 로 요청 전달
   ▼
[dokkaebi-ai / FastAPI]  이벤트 루프가 받음
   │  llm_semaphore 게이트 통과 (동시 N개 제한) → LLM 호출(await)
   │  ← 기다리는 동안 다른 요청도 처리 (논블로킹)
   ▼
[LLM 응답] → 결과를 server로 반환 → Redis에 캐시 저장 → 사용자에게 응답
```

각 서버는 각자 **프로세스**, 그 안에서 **스레드/이벤트루프**가 인스트럭션을 실행,
데이터는 **메모리(Redis, 힙)** 와 **디스크(DB, dump.rdb)** 를 오간다.
→ CSAPP 1장에서 배운 부품들이 그대로 백엔드 아키텍처가 된다.

## 6.5. 내 프로젝트 4개로 보는 동시성 모델 총정리 (speaknote · WeCam · 도깨비)

내가 만든 백엔드들을 실제로 열어보니, **동시성 모델의 거의 모든 유형**이 다 들어있었다.
이거 하나로 이 단원이 완성된다.

### 내 프로젝트 실제 스택
| 프로젝트 | 서버(백엔드) | AI 서버 | 특이점 |
|---|---|---|---|
| **WeCam** | Spring Boot **MVC** (`starter-web`) | OCR API (Python) | 순수 **스레드 풀** 방식 |
| **speaknote** | Spring Boot **MVC + WebFlux** (`webflux`+`websocket`) | **Flask** + LangChain(RAG) | 스레드 풀 + **이벤트 루프 둘 다** |
| **도깨비** | **NestJS** (Node.js) + Socket.io | **FastAPI** (uvicorn) | 둘 다 이벤트 루프 |

### 핵심 발견 ① WeCam Spring = "교과서적인 스레드 풀"
- WeCam 백엔드는 `spring-boot-starter-web` = **Spring MVC**. 앞 1장에서 이론으로 설명한
  **thread-per-request(요청당 스레드, 블로킹)** 모델 그 자체다.
- 요청 오면 톰캣 스레드 풀에서 스레드 하나 배정 → DB(JPA)·Redis 기다리는 동안 그 스레드는 블로킹.

### 핵심 발견 ② speaknote Spring = MVC + WebFlux (같은 JVM인데 두 모델 공존!)
speaknote는 `starter-web`(MVC) **과** `starter-webflux` **를 둘 다** 넣었다. 이게 중요하다:

> **WebFlux = JVM 진영의 "이벤트 루프" 답안.** (Netty 기반, 논블로킹)

- 즉 **"Spring Boot = 무조건 스레드 풀"이 아니다.** WebFlux를 쓰면 Spring도 FastAPI/NestJS처럼
  **적은 스레드로 논블로킹 처리**를 한다.
- speaknote가 `websocket`도 쓰니, 실시간·스트리밍(LLM 응답 흘려보내기)엔 이벤트 루프형이 유리해서 섞은 것.
- 정리하면 **동시성 모델은 "언어"가 아니라 "선택한 방식"이 결정한다.**
  같은 Java/Spring이라도 MVC(스레드풀) vs WebFlux(이벤트루프)를 고를 수 있다.

### 핵심 발견 ③ speaknote AI = Flask (FastAPI 아님!) — 동기 방식
- speaknote AI 서버는 **Flask**(+ LangChain RAG). Flask는 기본적으로 **동기(WSGI)** 프레임워크.
- FastAPI(async 이벤트 루프)와 달리, Flask는 기본이 **요청당 블로킹** → **gunicorn으로 워커(프로세스) 여러 개**를 띄워 동시성을 번다.
- 즉 같은 파이썬 AI 서버라도 **speaknote(Flask, 동기) vs 도깨비(FastAPI, 비동기)** 로 모델이 다르다.

### 핵심 발견 ④ WeCam AI(OCR) = CPU 바운드 → 이벤트 루프가 답이 아님
- OCR/딥러닝 추론은 **CPU/GPU를 오래 붙잡는 계산(CPU-bound)**.
- 이런 건 이벤트 루프에 넣으면 **루프가 그동안 막혀서** 오히려 독. → **프로세스/워커를 늘리거나 별도 워커 큐**로 뺀다.
- 반대로 LLM API 호출(도깨비-ai)은 **응답을 기다리는 I/O-bound** → 이벤트 루프가 최적.

---

## 6.6. 그래서 결론: 어떤 모델을 언제 쓰나 (판단 기준)

> **일이 "기다리는 일(I/O)"이냐 "계산하는 일(CPU)"이냐가 모든 걸 결정한다.**

| 작업 성격 | 예 (내 프로젝트) | 적합한 모델 | 이유 |
|---|---|---|---|
| **I/O 바운드** (기다림 많음) | LLM 호출(도깨비-ai), DB/Redis 조회, 소켓 | **이벤트 루프** (FastAPI, WebFlux, Nest) | 기다리는 시간에 딴 요청 처리 → 스레드 낭비 X |
| **CPU 바운드** (계산 많음) | OCR(WeCam-ai), 이미지/영상 처리, 대규모 연산 | **멀티 프로세스/워커** | 코어를 꽉 채워 병렬 계산, 루프 막힘 방지 |
| **복잡한 트랜잭션·성숙한 생태계** | 결제, 정산, 권한(WeCam/speaknote Spring) | **스레드 풀** (Spring MVC) | 코드가 직관적(동기), JPA·트랜잭션 성숙 |

**하드웨어로 되돌아가면:**
- I/O 바운드 = CPU는 놀고 **네트워크/디스크를 기다림** → 스레드를 붙잡아두면 낭비 → 이벤트 루프로 양보.
- CPU 바운드 = **CPU 자체가 병목** → 코어 수만큼 프로세스를 돌려 물리적으로 병렬화하는 수밖에 없음.
- 그래서 "스레드를 늘릴까 / 프로세스를 늘릴까 / 비동기로 바꿀까"는 **결국 이 작업이 CPU를 쓰는지 기다리는지**에서 갈린다. → **1장의 CPU·메모리·디스크·I/O 개념이 아키텍처 결정의 근거가 된다.**

---

## 6.7. 하드웨어 흐름으로 본 Spring Boot vs FastAPI 요청 처리

앞 문서(5.8)의 **NIC → I/O 버스 → I/O 브릿지 → 메모리 버스 → 메모리 → CPU** 하드웨어 길을,
실제 요청 코드에 대입해보자. **두 모델의 진짜 차이는 "I/O를 기다리는 동안 하드웨어가 뭘 하느냐"** 에 있다.

### 공통 시작: 요청이 서버 메모리에 도착하기까지 (여기까진 똑같다)
```
[클라이언트] HTTP 요청
  → [서버 NIC(랜카드)]           ← NIC도 I/O 버스에 붙은 I/O 장치일 뿐
  → I/O 버스 → [I/O 브릿지] → 메모리 버스
  → [메인 메모리]의 소켓 수신 버퍼에 요청 데이터가 쌓임
  → (DMA로 CPU 안 거치고 옮겨짐 + 다 오면 인터럽트로 CPU에 알림)
```
Spring이든 FastAPI든 **여기까진 완전히 동일**하다. 차이는 이 다음, "이걸 누가/어떻게 처리하느냐".

---

### Spring Boot (MVC) — 스레드 하나가 끝까지 붙잡고, 기다릴 땐 블로킹

예제 (WeCam 스타일: 유저 조회 → DB):
```java
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) {
    return userRepository.findById(id)   // ← DB 조회 (디스크까지 다녀옴, 느림)
                         .orElseThrow();
}
```

하드웨어에서 벌어지는 일:
```
1. 톰캣이 스레드풀에서 [스레드 A] 하나 꺼내 이 요청에 배정
   → 스레드 A의 스택(메모리)에 지역변수·호출정보가 쌓임

2. [CPU]가 스레드 A의 인스트럭션을 Fetch-Decode-Execute (레지스터↔ALU)

3. findById() 실행 → DB로 쿼리 요청이 다시
   NIC/디스크컨트롤러 → I/O 버스 → ... 로 나감 (I/O 시작)

4.  여기가 핵심: DB 응답이 올 때까지 [스레드 A]는 "블로킹(대기)" 상태로 멈춤
   - CPU는 스레드 A를 잠시 재우고(문맥 교환), 다른 스레드 B로 갈아탐
   - 하지만 스레드 A 자체는 "이 요청 전용"으로 계속 붙잡혀 있음 (스택 메모리도 점유)

5. DB 응답 도착 → 디스크/NIC 컨트롤러가 [인터럽트]로 CPU에 알림
   → CPU가 스레드 A를 깨워(문맥 교환) 이어서 실행 → 응답을 메모리에 만들고 NIC로 전송
```
- **비용:** 요청 1000개 동시 = 스레드 1000개 필요 → **스택 메모리 1000개분 + 문맥 교환 비용** 폭증.
- 그래서 스레드 풀 크기(기본 200)에 막히면 나머지는 큐에서 대기.
- **장점:** 코드가 위→아래로 그냥 읽힘(동기). 디버깅·트랜잭션 관리가 직관적.

---

### FastAPI (async) — 스레드 1개가, 기다리는 동안 딴 요청을 처리

예제 (도깨비-ai 스타일: LLM 호출):
```python
@router.post("/recommend")
async def recommend(req: Req):
    async with llm_semaphore:                 # 동시 N개 제한 게이트
        result = await call_llm(req.prompt)   # ← await: "응답 기다리는 동안 자리 비켜줌"
    return result
```

하드웨어에서 벌어지는 일:
```
1. [스레드 딱 1개]가 이벤트 루프를 돌리며 요청 A를 처리 시작

2. [CPU]가 그 스레드의 인스트럭션 실행 (여기까진 Spring과 같음)

3. await call_llm() 도달 → LLM API로 요청이 NIC → I/O 버스 로 나감 (I/O 시작)

4.  여기가 핵심: 스레드가 멈추지 않는다!
   - "요청 A는 응답 기다리는 중" 이라고 메모(코루틴 상태 저장)만 하고
   - 같은 스레드가 곧바로 요청 B, C, D... 를 이어서 처리
   - → 스레드 하나가 CPU를 놀리지 않고 계속 일함

5. LLM 응답 도착 → NIC 컨트롤러가 [인터럽트] → 이벤트 루프가
   "아 A 응답 왔네" 하고 A를 이어서 마저 처리 → 응답 전송
```
- **비용:** 요청 1000개 동시라도 **스레드는 1개(+워커 몇 개)** → 스택 메모리 최소, 문맥 교환 거의 없음.
- **단점:** ① `await` 없이 무거운 CPU 계산을 하면 루프가 막혀 나머지 요청 전부 멈춤.
  ② 코드가 async/await로 얽혀 흐름 추적이 어려움.

---

### 그림으로 나란히 비교 (I/O 대기 순간)

```
[Spring MVC]  요청마다 전용 스레드, 기다릴 땐 그 스레드가 통째로 대기
  요청A → 스레드A ──(DB 대기 중, 스레드A 붙잡힘/블로킹)──▶ 재개
  요청B → 스레드B ──(DB 대기 중, 스레드B 붙잡힘)──▶ 재개
  요청C → 스레드C ...                     (동시 처리량 = 스레드 개수)

[FastAPI async]  스레드 1개가 대기 시간마다 다른 요청으로 갈아탐
  스레드1: A시작→(A대기, B로)→B시작→(B대기, C로)→C시작→(A응답옴, A재개)→...
                                          (동시 처리량 = 대기가 많을수록 ↑)
```

### 하드웨어 관점 한 줄 정리
- **똑같은 인터럽트/DMA/버스**를 쓰지만,
  **I/O를 기다리는 그 순간에 "스레드를 붙잡아 두느냐(Spring MVC)" vs "스레드를 딴 일에 돌리느냐(FastAPI)"** 가 유일한 본질적 차이다.
- 그래서 **기다림이 많은 일(I/O 바운드)** 엔 FastAPI가, **CPU를 꽉 쓰는 일(CPU 바운드)** 이나 **복잡한 트랜잭션** 엔 Spring MVC가 유리하다. (speaknote의 WebFlux는 Spring으로 FastAPI식 이점을 얻으려는 선택)

---

## 7. 최종 정리

1. 웹서버 = **종료 안 하고 소켓을 계속 읽는 프로세스** 하나.
2. **JVM(Spring)/파이썬(FastAPI)/V8(Nest)** = 내 코드를 CPU가 실행하게 통역하는 "가상 프로세서".
3. **Spring Boot = 스레드 풀(요청당 스레드, 블로킹)** vs **FastAPI/NestJS = 단일 스레드 이벤트 루프(논블로킹)**.
4. 내 도깨비 프로젝트는 **server(Nest)·ai(FastAPI) 둘 다 이벤트 루프** 진영.
5. `llm_semaphore` = 이벤트 루프의 무한 동시성을 **N개로 제한**하는 동시성 제어(세마포어).
6. **스레드=일꾼 / 메모리=책상(Redis 힙) / 디스크=창고(DB, dump.rdb)** — 1장 하드웨어 개념이 실무 그 자체.
