# 프로세서는 메모리에 저장된 인스트럭션을 읽고 해석한다

## 0. 한 줄 요약

> `./hello` 를 치면 → **쉘**이 명령을 받아 → **디스크**에 있던 실행파일을 **메모리**로 옮기고 →
> **프로세서(CPU)** 가 메모리 속 **인스트럭션을 하나씩 읽어 실행**해서 → 화면에 `hello, world` 를 띄운다.
> 이 전 과정을 움직이는 부품들의 구성이 **하드웨어 조직(organization)** 이다.

---

## 1. 인스트럭션(instruction)이란? — 가장 중요한 개념

### 정의
> **인스트럭션 = CPU가 "한 번에 할 수 있는 가장 작은 단위의 명령" 하나.**

우리가 `printf("hello")` 라고 쓴 건 사람 기준의 "한 줄"이지만,
CPU에겐 너무 큰 덩어리라 **여러 개의 인스트럭션으로 잘게 쪼개진다.**
(앞에서 본 `hello.s`의 `mov`, `add`, `bl`, `ret` 하나하나가 인스트럭션이다.)

### 비유 ① 레시피의 한 동작
"계란찜을 만들어라"(printf) = 사람 명령.
CPU는 이걸 못 알아듣는다. CPU가 아는 건 이 정도로 잘게 쪼갠 것뿐:
```
① 그릇을 집어라        (LOAD)
② 계란을 그릇에 넣어라  (STORE)
③ 저어라               (연산)
④ 다음 단계로 가라      (JUMP)
```
이 **한 동작 하나하나가 인스트럭션**이다. CPU는 이런 초단순 동작만 할 줄 안다.
대신 **1초에 수십억 번** 해서 복잡한 일을 해낸다.

### 비유 ② 레고 설명서의 한 페이지
멋진 성(프로그램)도, 설명서를 넘겨보면 결국 **"1번 블록 위에 2번 블록 끼우기"** 같은
**단순 스텝의 연속**이다. 인스트럭션이 그 스텝 하나다.

### CPU가 아는 인스트럭션은 딱 몇 종류뿐
놀랍게도 CPU가 이해하는 명령의 "종류"는 몇 가지 안 된다:
| 종류 | 하는 일 | 비유 |
|---|---|---|
| **Load (읽기)** | 메모리 → 레지스터로 값 가져오기 | 창고에서 작업대로 물건 꺼내기 |
| **Store (쓰기)** | 레지스터 → 메모리로 값 저장 | 작업대에서 창고로 물건 넣기 |
| **Operate (연산)** | 두 값 더하기/빼기 등 계산 | 작업대에서 조립·계산 |
| **Jump (점프)** | 다음에 실행할 위치를 바꾸기 | 설명서 페이지 건너뛰기 (if/for/함수호출) |

> 컴퓨터가 하는 모든 일 = 이 단순한 인스트럭션 수십억 개의 조합.

## 1.5. 적재·저장·연산·점프 — 백엔드 코드로 이해하기 (Spring Boot / FastAPI)

네 가지 명령이 추상적으로 느껴질 텐데, **내가 매일 짜는 백엔드 코드 한 줄이 이 넷으로 쪼개진다.**
먼저 큰 그림부터.

> **메인 메모리 = 데이터 창고, 레지스터 = CPU 손에 쥔 작업대.**
> CPU는 창고(메모리)에서 직접 계산하지 못한다. 반드시
> **① 창고→작업대로 꺼내고(적재/Load) → ② 작업대에서 계산하고(연산/Operate) → ③ 작업대→창고로 넣는다(저장/Store).**
> 그리고 **어느 코드로 갈지 방향을 트는 게 점프(Jump)** 다 (if/for/함수 호출).

### 예제 ① Spring Boot — 주문 총액 계산

```java
@GetMapping("/orders/{id}/total")
public int total(@PathVariable Long id) {
    Order order = orderRepository.findById(id).orElseThrow();
    int sum = 0;
    for (Item item : order.getItems()) {
        sum = sum + item.getPrice();
    }
    if (order.isVip()) {
        sum = (int)(sum * 0.9);
    }
    return sum;
}
```

한 줄씩 CPU 명령으로 번역하면:

| 코드 | CPU가 실제로 하는 일 | 명령 종류 |
|---|---|---|
| `int sum = 0;` | 값 0을 sum의 메모리 자리에 써넣음 | **저장 (Store)** |
| `item.getPrice()` | 메모리에 있는 item의 가격을 레지스터로 꺼냄 | **적재 (Load)** |
| `sum + item.getPrice()` | 레지스터 두 값을 ALU로 더함 | **연산 (Operate)** |
| `sum = (더한 값)` | 더한 결과를 다시 sum 자리에 써넣음 | **저장 (Store)** |
| `for (...)` 반복 | 블록 끝에서 다시 for 시작으로 PC를 되돌림 | **점프 (Jump)** |
| `if (order.isVip())` | 조건이 거짓이면 if 블록을 건너뛰게 PC 이동 | **점프 (Jump)** |
| `sum * 0.9` | 곱셈 계산 | **연산 (Operate)** |
| `return sum;` | 이 함수를 호출한 곳으로 PC 복귀 | **점프 (Jump)** |

### 예제 ② FastAPI — 똑같은 로직, 파이썬

```python
@router.get("/orders/{id}/total")
def total(id: int):
    order = get_order(id)
    total = 0
    for item in order.items:
        total = total + item.price
    if order.is_vip:
        total = int(total * 0.9)
    return total
```

언어만 다를 뿐 **CPU가 쪼개는 방식은 완전히 동일**하다:
- `total = 0` → **저장**
- `item.price` 값 읽기 → **적재**
- `total + item.price` → **연산**
- 그 결과를 `total`에 → **저장**
- `for` 반복 → **점프**(뒤로), `if` 분기 → **점프**(조건), `return` → **점프**(복귀)

> **핵심 통찰:** Java든 Python이든, 고급 언어의 문법은 결국
> **"메모리에서 꺼내고(적재) → 계산하고(연산) → 도로 넣고(저장) → 어디로 갈지 정한다(점프)"** 이 네 동작의 조합으로 번역된다.
> 우리가 `sum = sum + price` 라고 쓴 한 줄이, CPU에겐 **적재 → 연산 → 저장** 세 스텝인 것.

### 왜 굳이 "적재"하고 "저장"할까? (메모리 vs 레지스터)

- **CPU는 메모리 값을 직접 계산하지 못한다.** 반드시 레지스터(작업대)로 꺼내와야(적재) 계산할 수 있다.
- 레지스터는 **극소량**(수십 개)이라, 계산이 끝난 값은 다시 메모리(창고)에 넣어둬야(저장) 자리를 비운다.
- 그래서 `sum = sum + price` 조차 → **① sum 적재 → ② price 적재 → ③ 덧셈(연산) → ④ sum에 저장** 으로 잘게 나뉜다.
- 이 "적재/저장" 왕복이 잦을수록 느려지기 때문에, 뒤에 배울 **캐시**가 이 왕복을 빠르게 만들어 주는 것.

> 백엔드 한 줄 요약:
> **변수 대입 = 저장 / 변수·필드 읽기 = 적재 / +, ×, 비교 = 연산 / if·for·메서드 호출·return = 점프.**
> 내가 짠 엔드포인트 하나가, 이 네 가지 명령 수백만 개로 번역되어 CPU 위에서 돈다.

## 2. 하드웨어 조직 (Hardware Organization)

`hello` 하나가 실행되는 무대에 등장하는 부품들. 크게 **4가지**다.

```
        ┌──────────────────── CPU (프로세서) ────────────────────┐
        │   [PC] → 다음 인스트럭션 주소                            │
        │   [레지스터 파일] 초고속 임시 저장소 (아주 작음)          │
        │   [ALU] 계산 담당 (덧셈/뺄셈/비교…)                      │
        └───────────────────────┬────────────────────────────────┘
                                 │  ← 시스템 버스 (데이터 고속도로)
        ┌────────────────────────┴───────────────────────────────┐
        │                    메인 메모리 (DRAM)                     │
        │        실행 중인 프로그램 + 데이터를 임시로 담음           │
        └────────────────────────┬───────────────────────────────┘
                                 │  ← I/O 버스
     ┌──────────┬────────────────┼──────────────┬────────────────┐
  [키보드]    [마우스]         [디스플레이]     [디스크]
                                              (프로그램·파일 영구 저장)
```

### ① CPU (프로세서) — "일하는 뇌"
메모리에서 인스트럭션을 하나 가져와 실행하고, 다음 걸 가져와 실행하고… 를 반복. 핵심 부품 셋:
- **PC (Program Counter):** "지금 실행할 인스트럭션이 메모리 몇 번지에 있나"를 가리키는 화살표.
  인스트럭션 하나 실행할 때마다 다음 걸로 이동. (책 읽을 때 짚어가는 손가락)
- **레지스터 파일 (Register File):** CPU 안의 **극소량·초고속** 저장 공간. 지금 당장 계산할 값 몇 개만 올려둠. (작업대 위)
- **ALU (산술논리연산장치):** 실제 계산(덧셈, 비교 등)을 하는 곳. (계산기)

### ② 메인 메모리 (Main Memory / DRAM) — "작업 책상"
- 실행 중인 프로그램의 **인스트럭션과 데이터**를 임시로 올려두는 곳.
- **빠르지만 휘발성** → 전원 끄면 다 날아감.
- 바이트마다 주소(번지)가 매겨진 거대한 배열이라고 보면 됨.

### ③ 입출력 장치 (I/O Devices) — "손·눈·귀"
- 키보드/마우스(입력), 디스플레이(출력), 디스크(저장).
- 각 장치는 **컨트롤러/어댑터**를 통해 시스템에 연결됨. (장치와 컴퓨터 사이의 통역사)

### ④ 버스 (Bus) — "데이터가 다니는 고속도로"
- 부품들 사이에 데이터를 실어 나르는 전선 묶음.
- 한 번에 **word(요즘 보통 8바이트) 단위**로 실어 나름.

## 3. 디스크 vs 메모리 — 왜 둘 다 필요한가? (핵심 구분)

초보가 제일 헷갈리는 부분. 둘 다 "저장"인데 역할이 완전히 다르다.

| | **디스크 (SSD/HDD)** | **메인 메모리 (DRAM)** |
|---|---|---|
| 역할 | **영구 보관** (파일, 프로그램) | 실행 중인 것만 **임시** 올려둠 |
| 전원 끄면 | 유지됨 O | 다 날아감 X (휘발성) |
| 속도 | 느림 (메모리의 수만~수십만 배 느림) | 빠름 |
| 용량 | 큼 (수백 GB~TB) | 작음 (수~수십 GB) |
| 비유 | **책장/창고** (책을 꽂아둠) | **책상** (지금 읽는 책만 펴둠) |

**왜 디스크 것을 굳이 메모리로 옮겨서 실행하나?**
CPU는 너무 빨라서, 느린 디스크에서 직접 인스트럭션을 읽으면 **CPU가 하염없이 기다려야** 한다.
그래서 실행 직전에 프로그램을 **빠른 메모리로 통째로 복사**해두고, CPU는 메모리에서만 읽는다.
(도서관 서고까지 매번 다녀오지 않고, 필요한 책을 책상에 올려두고 보는 것과 같음)

## 4. 쉘(Shell)과 인터프리터(Interpreter)

### 쉘이란?
> **쉘 = 사용자가 친 명령어를 받아 대신 실행해주는 프로그램.** (터미널에 뜨는 그거)

- 프롬프트(`$`)를 띄우고 → 내가 명령을 칠 때까지 기다리고 → 엔터 치면 실행.
- `./hello`, `ls`, `cd` … 이런 걸 내가 치면 쉘이 받아서 처리한다.
- 대표: bash, zsh(맥 기본).

### 인터프리터란? (쉘도 인터프리터의 일종)
> **인터프리터 = 명령/코드를 "한 줄씩 읽어서 그때그때 바로 실행"하는 프로그램.**

- 쉘은 내 명령어를 한 줄씩 읽어 즉시 실행하니까 **명령어 인터프리터**다.
- Python도 인터프리터: `.py`를 미리 기계어로 다 번역(컴파일)하지 않고, 한 줄씩 읽어 실행.

### 비유: 통역 방식의 차이
| | 컴파일러 (Compiler) | 인터프리터 (Interpreter) |
|---|---|---|
| 방식 | 책 **전체를 미리 다 번역**해서 번역본을 건넴 | **한 문장씩 실시간 통역** |
| 예 | C (gcc로 미리 실행파일 생성) | 쉘, 파이썬 |
| 장점 | 실행이 빠름 | 바로바로 실행, 유연함 |
| 단점 | 번역(빌드) 시간 필요 | 실행이 상대적으로 느림 |

> 앞 단원에서 한 `gcc`가 **컴파일러**, 지금 `./hello`를 받아주는 게 **쉘(인터프리터)**.

## 5. 전체 흐름: `./hello` 를 치면 실제로 벌어지는 일

부품들이 어떻게 협력하는지 순서대로.

```
1. 내가 키보드로 "./hello" 타이핑
   → 각 글자가 [키보드] → 버스 → [메모리]로 들어감. 쉘이 그걸 화면에 보여줌.

2. 엔터(Enter) 키를 누름
   → "명령 입력 끝!" 신호. 쉘이 "./hello 를 실행하라"는 뜻으로 해석.

3. 쉘이 실행파일 hello 를 [디스크]에서 찾아 [메모리]로 복사(로드)
   → 이때 CPU를 안 거치고 디스크→메모리 직접 전송(DMA)해서 CPU는 딴 일 가능.
      (책장에서 책을 꺼내 책상에 펼침)

4. [CPU]가 메모리에 올라온 hello의 인스트럭션을 PC가 가리키는 순서대로 하나씩 실행
   → 그 안엔 "hello, world\n 이라는 데이터를 화면으로 보내라"는 인스트럭션들이 있음.

5. "hello, world\n" 문자열이 [메모리] → 버스 → [디스플레이]로 전달
   → 화면에 hello, world 출력! 
```

> **정리:** CPU가 하는 일은 결국 딱 하나 —
> **"PC가 가리키는 메모리 속 인스트럭션을 읽어 → 해석해 → 실행하고 → PC를 다음으로 옮긴다"**
> 이 단순 반복(fetch-decode-execute)을 초당 수십억 번 하는 것.

## 5.5. 프로세서(Processor) vs 프로세스(Process) — 헷갈리지 말자

이름 한 글자 차이라 정말 많이 헷갈리는데, **완전히 다른 것**이다.

| | **프로세서 (Processor)** | **프로세스 (Process)** |
|---|---|---|
| 정체 | **하드웨어** (물리적 부품, CPU) | **소프트웨어** (실행 중인 프로그램) |
| 무엇 | 인스트럭션을 실행하는 **칩** | 지금 돌아가고 있는 **프로그램 하나** |
| 개수 | 컴퓨터에 몇 개 (코어 수만큼) | 동시에 수백~수천 개 가능 |
| 손에 잡히나 | O 만질 수 있는 물건 | X 개념(메모리+실행상태) |
| 예 | 인텔 i7, 애플 M3 칩 | 지금 켜둔 크롬, 카톡, `./hello` 실행 |

### 비유: 요리사 vs 주문서
- **프로세서 = 요리사**(실제로 요리하는 사람, 물리적 존재).
- **프로세스 = 진행 중인 주문 하나**("3번 테이블 파스타 조리 중"이라는 작업 상태).
- 요리사(프로세서)는 몇 명 안 되지만, 진행 중인 주문(프로세스)은 수십 개일 수 있다.
- 요리사가 주문들 사이를 **빠르게 왔다갔다** 하며 조금씩 처리하면, 손님들은 "내 주문이 계속 진행되네"라고 느낀다.
  → 이게 CPU가 프로세스를 번갈아 처리하는 **문맥 교환(context switch)**. 그래서 코어 몇 개로도 수백 개 프로그램이 동시에 도는 것처럼 보인다.

> **프로세서는 "실행하는 주체(하드웨어)", 프로세스는 "실행되고 있는 대상(소프트웨어)".**
> (참고로 *프로세스*는 CSAPP 뒤쪽 "운영체제의 추상화" 단원에서 본격적으로 다룬다.)

## 5.7. PC(Program Counter)는 실제로 어떻게 움직이나 — 진짜 예시로 추적

앞에서 만든 `hello`를 `objdump -d` 로 뜯으면 이렇게 생겼다. (왼쪽 숫자가 **메모리 주소**)
> ARM64는 **인스트럭션 하나가 정확히 4바이트** → 그래서 보통 PC가 **+4씩** 이동한다.

```
주소   기계어      인스트럭션
 0:  d10083ff   sub  sp, sp, #0x20       ; 스택 공간 확보 (함수 시작)
 4:  a9017bfd   stp  x29, x30, [sp,#16]  ; 돌아갈 주소(x30) 저장 
 8:  910043fd   add  x29, sp, #0x10
 c:  52800008   mov  w8, #0x0            ; 반환값 0 준비
10:  b9000be8   str  w8, [sp, #0x8]
14:  b81fc3bf   stur wzr, [x29, #-0x4]
18:  90000000   adrp x0, ...             ; "hello, world\n" 주소 준비
1c:  91000000   add  x0, x0, ...
20:  94000005   bl   _printf             ; printf 호출  (여기서 점프!)
24:  b9400be0   ldr  w0, [sp, #0x8]      ; printf 끝나면 여기로 복귀 
28:  a9417bfd   ldp  x29, x30, [sp,#16]
2c:  910083ff   add  sp, sp, #0x20
30:  d65f03c0   ret                      ; main 종료, 호출한 곳으로 복귀 
```

### 상황 A) 평범할 땐 PC가 그냥 +4씩 전진 (순차 실행)

CPU는 **"PC가 가리키는 주소의 인스트럭션을 실행 → PC += 4 → 반복"** 만 한다.

```
PC = 0   → sub 실행   → PC = 4
PC = 4   → stp 실행   → PC = 8
PC = 8   → add 실행   → PC = c
PC = c   → mov 실행   → PC = 10
PC = 10  → str 실행   → PC = 14
PC = 14  → stur 실행  → PC = 18
PC = 18  → adrp 실행  → PC = 1c
PC = 1c  → add 실행   → PC = 20
```
> 책 읽을 때 손가락이 한 줄씩 자동으로 내려가는 것과 똑같다. (+4 = 다음 줄)

### 상황 B) 함수 호출 `bl` — PC가 "점프"하고, 돌아올 주소를 적어둠

`PC = 20` 의 `bl _printf` 가 실행되면 두 가지가 동시에 일어난다:

```
① 돌아올 주소를 저장: x30(link register) ← 24   (bl 다음 주소 = 20+4)
② PC를 printf 코드로 점프:      PC ← (printf가 있는 주소)
```
- **여기서 PC가 +4가 아니라 완전히 다른 곳(printf)으로 튄다.** 이게 "점프".
- 동시에 **"일 끝나면 24번지로 돌아와"** 를 x30에 메모해둔다.
  → 이게 1장 버퍼 오버플로우에서 본 **return address(복귀 주소)** 의 정체!
- printf 내부도 결국 인스트럭션들이라 PC가 그 안에서 또 +4씩 진행하며 실행됨.

```
PC = 20  → bl 실행 → [x30 = 24 저장]  → PC = printf 시작 주소
   ...  (printf 내부 인스트럭션들 실행, PC가 그 안을 돌아다님) ...
   printf 끝의 ret → PC = x30 = 24   ← 저장해둔 주소로 복귀!
PC = 24  → ldr 실행 → PC = 28        ← 아무 일 없던 듯 이어서 진행
```

### 상황 C) `ret` — 저장해둔 주소로 PC를 되돌림

`PC = 30` 의 `ret` 이 실행되면:
```
PC ← x30 (아까 stp로 저장해둔, main을 호출한 곳의 주소)
```
- main을 부른 쪽(C 런타임)으로 PC가 돌아가고, 결국 프로그램이 종료된다.

> **핵심:** `bl`(점프하며 복귀주소 저장) ↔ `ret`(복귀주소로 PC 되돌림) 이 짝을 이룬다.
> 이 "갔다가 정확히 제자리로 돌아오는" 메커니즘이 **함수 호출의 하드웨어적 실체**다.

### if / for 도 결국 PC 조작이다
- `if (조건)` → 조건이 거짓이면 **PC를 if 블록 건너뛴 곳으로 점프** (조건부 분기).
- `for` 반복 → 블록 끝에서 **PC를 반복 시작 지점으로 되돌림**(뒤로 점프). 조건 만족하면 탈출.
- 즉 우리가 짜는 모든 제어문은, CPU 입장에선 **"PC를 어디로 옮길까"의 문제**로 번역된다.

### 이 전체를 부르는 이름: Fetch–Decode–Execute 사이클
```
   ┌─────────────────────────────────────────┐
   ▼                                           │
[Fetch]  PC가 가리키는 주소에서 인스트럭션을 가져옴
   │
[Decode] 그게 무슨 명령인지 해석 (Load? Jump?)
   │
[Execute] 실행하고, PC를 갱신 (+4 또는 점프 주소로) ──┘  (무한 반복, 초당 수십억 번)
```

> **CPU의 일생 = 이 사이클을 전원 꺼질 때까지 반복하는 것.** PC는 그 사이클을 이끄는 지휘봉.

## 5.8. 하드웨어 전체에서 데이터가 흐르는 길 (버스 · I/O 브릿지 · 메모리)

PC는 CPU 안의 얘기였고, 이제 **부품들 사이를 데이터가 어떻게 오가는지** 전체 지도를 보자.

### 먼저: 버스 계층 지도

부품들은 아무렇게나 연결된 게 아니라 **여러 층의 버스**로 이어져 있다.
가운데에 **I/O 브릿지**라는 교차로가 있어서, 빠른 쪽(CPU·메모리)과 느린 쪽(I/O 장치)을 중계한다.

```
        ┌─────────────── CPU ───────────────┐
        │  [레지스터 파일] ⇄ [ALU]           │   ← CPU 내부 (제일 빠름)
        │        ▲  PC가 지휘                 │
        └────────┼───────────────────────────┘
                 │  ① 시스템 버스 (System Bus)
                 ▼
        ┌──────────────────┐   ② 메모리 버스 (Memory Bus)   ┌──────────────┐
        │   I/O 브릿지       │ ◀───────────────────────────▶ │ 메인 메모리   │
        │  (교차로/중계소)   │                                │  (DRAM)      │
        └────────┬─────────┘                                └──────────────┘
                 │  ③ I/O 버스 (I/O Bus) — 상대적으로 느림
     ┌───────────┼─────────────┬──────────────┐
 [USB 컨트롤러]  [그래픽 어댑터]  [디스크 컨트롤러]  ...
   │      │           │              │
[키보드][마우스]   [디스플레이]      [디스크]
```

- **① 시스템 버스:** CPU ↔ I/O 브릿지. CPU가 바깥세상과 통하는 첫 관문.
- **② 메모리 버스:** I/O 브릿지 ↔ 메인 메모리. **CPU-메모리는 이 짧고 빠른 길로 데이터 교환.**
- **③ I/O 버스:** I/O 브릿지 ↔ 각종 장치(키보드·화면·디스크). **느린 장치들이 붙는 통로.**
- **I/O 브릿지 = 교차로/중계소.** 빠른 도로(시스템·메모리 버스)와 느린 도로(I/O 버스)가 만나는 나들목.
- 각 장치는 **컨트롤러/어댑터**(USB 컨트롤러, 그래픽 어댑터, 디스크 컨트롤러)를 거쳐 I/O 버스에 붙는다. (장치와 버스 사이의 통역사)

---

### 이제 `./hello` 를 실행하는 전 과정을 데이터 흐름으로 (CSAPP 핵심 3장면)

#### 장면 1) 키보드로 "./hello" 를 친다 — 입력이 메모리로

```
[키보드] 글자 입력
  → [USB 컨트롤러]  (키 입력을 신호로 변환)
  → ③ I/O 버스
  → [I/O 브릿지]    (교차로에서 방향 전환)
  → ② 메모리 버스
  → [메인 메모리]   (쉘이 읽을 수 있게 문자들이 메모리에 쌓임)
```
- 이때 쉘 프로그램이 이 글자들을 읽어(레지스터로) 화면에 되비춰준다(에코).
- **포인트:** 아무리 가까운 부품끼리도 데이터는 반드시 **버스라는 길을 타고** 이동한다.

#### 장면 2) Enter 를 누른다 — 디스크의 실행파일이 메모리로 (DMA )

쉘이 "hello 실행파일을 메모리로 올려라" 명령. 여기서 중요한 기법이 등장한다.

```
[디스크]의 hello 실행파일
  → [디스크 컨트롤러]
  → ③ I/O 버스 → [I/O 브릿지] → ② 메모리 버스
  → [메인 메모리]에 코드+데이터가 통째로 복사됨
```
- **DMA (Direct Memory Access):** 이 복사를 **CPU를 거치지 않고** 디스크→메모리로 **직접** 한다.
- 왜? 디스크는 너무 느려서, CPU가 일일이 나르면 그동안 CPU가 놀아야 한다.
  → **CPU는 딴 일 하고, 데이터 운반은 DMA에게 맡김.** (택배를 내가 직접 안 가고 택배기사에게 맡기는 것)
- 복사가 끝나면 디스크 컨트롤러가 CPU에게 **인터럽트**로 "다 옮겼어요" 라고 알림.

#### 장면 3) CPU가 실행한다 — 메모리↔CPU↔화면

이제 프로그램이 메모리에 있으니, CPU가 5.7에서 본 **Fetch-Decode-Execute** 를 돌린다.

```
(가) 인스트럭션/데이터 읽기:
  [메인 메모리] → ② 메모리 버스 → [I/O 브릿지] → ① 시스템 버스 → [CPU 레지스터 파일]
  → PC가 가리키는 인스트럭션을 가져와 ALU로 실행

(나) 출력하기: "hello, world\n" 문자열을 화면으로
  [CPU/메모리] → 시스템/메모리 버스 → [I/O 브릿지]
  → ③ I/O 버스 → [그래픽 어댑터] → [디스플레이]
  → 화면에 hello, world 표시 
```
- 즉 CPU는 **메모리에서 데이터를 레지스터로 당겨와(Load) 계산하고, 결과를 다시 메모리나 장치로 내보낸다(Store).**
- 이 모든 이동이 **버스 → I/O 브릿지 → 버스** 를 거친다.

---

### 왜 이렇게 층을 나눴나? (속도 차이 때문)

부품마다 속도가 **천차만별**이라, 빠른 것끼리·느린 것끼리 묶어야 전체가 안 느려진다.

```
빠름 ────────────────────────────────────▶ 느림
레지스터  >  메모리(DRAM)  >>  디스크(SSD)  >>>  네트워크
(CPU 안)    (메모리 버스)     (I/O 버스)       (바깥)
```
- 그래서 **레지스터·메모리는 빠른 버스(시스템/메모리)** 로, **디스크·키보드는 느린 I/O 버스**로 분리.
- **I/O 브릿지**가 이 속도 다른 세계를 중계하는 핵심. (고속도로 ↔ 국도 나들목)
- 이 "속도 계층"이 뒤에 배울 **메모리 계층구조(캐시)** 의 출발점이다.

### 백엔드 요청 하나에 그대로 대입하면

내 서버에 HTTP 요청이 들어올 때도 **똑같은 하드웨어 길**을 탄다:

```
[네트워크 카드(NIC)]  요청 패킷 도착
  → I/O 버스 → [I/O 브릿지] → 메모리 버스 → [메인 메모리]의 소켓 버퍼   (장면 1과 동일)
  → [CPU]가 메모리에서 요청 데이터를 레지스터로 읽어와 처리            (장면 3-가)
  → DB 조회 필요하면 → 디스크 컨트롤러 → 디스크 (느림!)              (그래서 캐시를 쓴다)
  → 응답을 메모리에 만들고 → NIC 통해 네트워크로 내보냄               (장면 3-나)
```
- NIC(랜카드)도 결국 **I/O 버스에 붙은 하나의 I/O 장치**다. 키보드·디스크와 같은 계층.
- "DB가 느리다"는 말의 하드웨어적 실체 = **느린 I/O 버스 너머 디스크까지 다녀와야 한다**는 것.
- Redis 캐시가 빠른 이유 = 그 왕복을 생략하고 **빠른 메모리 버스 안에서 끝내기** 때문.

## 6. 최종 정리

1. **인스트럭션** = CPU가 한 번에 하는 가장 작은 명령(Load/Store/연산/Jump). 프로그램은 이것들의 거대한 조합.
2. **하드웨어 조직** = CPU(PC·레지스터·ALU) + 메모리 + I/O장치 + 버스, 이 넷이 협력.
3. **디스크(영구·느림·책장) vs 메모리(임시·빠름·책상)** — 실행 땐 디스크→메모리로 옮겨 CPU가 빠르게 읽음.
4. **쉘** = 내 명령어를 받아 실행해주는 **인터프리터** 프로그램.
5. **CPU의 본질** = PC가 짚는 인스트럭션을 읽고-해석하고-실행하는 것을 무한 반복(fetch-decode-execute).
